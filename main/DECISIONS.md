# Decisions & Assumptions

Deviations from, or unspecified choices left to, [docs/README.md](../docs/README.md).

- **Project layout:** the Next.js app lives in `main/` (a subfolder of the repo root), with `docs/` next to it holding the spec. All paths in the README/task plan that assume the app is at the repo root (e.g. `src/`, `prisma/`) are relative to `main/` instead.
- **Postgres host port:** mapped to `5433` on the host in `docker-compose.yml` (container still listens on `5432` internally) to avoid colliding with a local Postgres instance already using the default port.
- **Prisma pinned to 6.19.3 (exact):** Prisma 7 removed the classic `datasource { url = env("DATABASE_URL") }` schema pattern in favor of a `prisma.config.ts` file plus a driver adapter (e.g. `@prisma/adapter-pg`). That's extra setup the README doesn't anticipate, so we pinned `prisma` and `@prisma/client` to the last stable 6.x release (`6.19.3`, exact version to avoid drifting to 7/8 on a future install) and kept the simple schema-based config.
- **Design tokens taken from literals, not CSS variables:** the prototype (`docs/design-reference/Sprint Planner.dc.html`) defines colors/sizes as inline literals rather than `:root` custom properties. `docs/design-reference/TOKENS.md` was built by grepping those literals (plus the `PB` priority-badge config object) and cross-checking against the 31 reference screenshots, then mapped into Tailwind's `@theme` in `main/src/app/globals.css`.
- **Priority badge colors:** DESIGN.md only says "gray / amber / red"; the prototype defines exact hexes (low `#F1F5F9`/`#334155`/`#64748B` dot, medium `#FEF3C7`/`#92400E`/`#D97706` dot, high `#FEE2E2`/`#991B1B`/`#DC2626` dot). Per the instruction that the prototype wins on visual details, these exact values were used.
- **No web font:** the prototype loads no web font and uses the system font stack (`-apple-system, BlinkMacSystemFont, "Segoe UI", system-ui, Ubuntu, "Helvetica Neue", sans-serif`). DESIGN.md allows Inter as an option but defaults to system fonts; since the prototype (visual authority) uses system fonts, the default Next.js Geist font loading was removed from `layout.tsx` to match.
- **Dark mode:** not implemented. DESIGN.md marks dark mode optional/"support light mode first" and it's out of scope for design (section 10); the prototype itself is light-only. `globals.css` defines a single light palette instead of a light/dark pair.
- **Disabled Next 16 `cacheComponents`/`partialPrefetching`:** the scaffold enabled these experimental flags by default. They require every dynamic data read (`cookies()`, `searchParams`, uncached fetches) to be wrapped in `<Suspense>` or explicitly cached, or the build fails. Since this app is entirely session-gated (virtually every page reads the session/cookies) with no static-generation benefit, this fights the architecture for no gain, so both flags were turned off in `next.config.ts` — the simplest option.
- **`middleware.ts` kept despite Next 16 deprecation warning:** Next 16 deprecates the `middleware.ts` convention in favor of `proxy.ts` (same behavior, new name). Kept the README's exact specified filename (`middleware.ts`, section 5/12) since it still works (warning only, not an error); can be renamed later with `npx @next/codemod middleware-to-proxy` if desired.
- **Two auth-helper variants:** README section 5 asks for a single `requireUser()`/`requireAdmin()` pair used by "every route handler and protected server component." In practice a route handler must return a JSON `{error}` on failure (section 7) while a server-component page should redirect to `/login` (DESIGN.md section 6, "session expired" behavior) — these are incompatible response shapes for one function. Implemented as `requireUser()`/`requireAdmin()` (throw an `AppError`, caught by route handlers and converted to JSON) plus `requireUserForPage()`/`requireAdminForPage()` (redirect directly, for server components), sharing the same underlying `getSession()` check.
- **Minimal placeholder home page:** `/` currently shows the signed-in user inside the shared `AppShell` instead of redirecting to `/sprints/current`, since the Sprint view doesn't exist yet (that's step 4). Will be replaced when sprints are built.
- **Vercel deploy fix — pnpm ignores postinstall scripts by default:** pnpm 10 (used on Vercel) skips dependency build/postinstall scripts unless explicitly allowed, which silently broke two things: `prisma generate` never ran (so `@prisma/client` had no generated code, failing the TypeScript build) and `bcrypt`'s native-binding setup was skipped. Fixed by (1) making `prisma generate` an explicit step in `package.json`'s `build` script, not just relying on the `postinstall` hook, and (2) adding `pnpm.onlyBuiltDependencies` to `package.json` to allow-list `@prisma/client`, `@prisma/engines`, `bcrypt`, `esbuild`, `prisma`, and `unrs-resolver`.
- **Production database: Neon, plain connection (not Vercel's Prisma Postgres/Accelerate):** Vercel's native "Prisma Postgres" marketplace integration sets `DATABASE_URL` to a Prisma Accelerate URL (`prisma+postgres://accelerate.prisma-data.net/...`), which our plain `@prisma/client` (no Accelerate extension, kept simple per the README) can't use directly — it would need `@prisma/extension-accelerate`. Since the user provisioned Postgres on Neon directly instead, `DATABASE_URL` is a standard `postgresql://` connection string and no code changes were needed; `src/lib/db.ts`/`prisma/schema.prisma` are unchanged.
- **Migrations and a safety-net admin user run automatically on every deploy:** `package.json`'s `build` script is `prisma generate && prisma migrate deploy && tsx prisma/ensure-admin.ts && next build`. `prisma migrate deploy` applies any pending migrations (no-op if already up to date — safe to run on every build). `prisma/ensure-admin.ts` is a new, production-safe script (unlike `prisma/seed.ts`, which is deliberately blocked outside development) that checks `prisma.user.count()` and creates one admin user from `SEED_ADMIN_EMAIL`/`SEED_ADMIN_PASSWORD` only if the table is empty — so a fresh database always has a way to log in, without re-seeding sample teams/sprints/tasks into production on every deploy. Verified locally against both a populated DB (skips) and a throwaway empty DB (creates the admin, applies migrations cleanly).
- **Environment variable values not shared in chat:** Vercel's dashboard hides values for "sensitive" env vars (and some were set by marketplace integrations) — by design, this is for secret-handling, not a bug. Rather than asking the user to paste connection strings into the conversation, the build was changed to rely only on env var *names* already matching our code (`DATABASE_URL`, `REDIS_URL`, etc., per `.env.example`) and to run migrate/seed steps server-side during the Vercel build, where Vercel injects the real values automatically.
- **Deployed on Render.com, not Vercel:** after working through the Vercel-specific build issues above, the user ultimately deployed the web service, Postgres, and Redis all on Render instead. The `prisma generate`/`migrate deploy`/`ensure-admin` build-script changes are host-agnostic and work the same way there.
- **Admin can't delete their own account:** not specified in README/DESIGN.md. Added as a minimal safety guard (the "Delete" row-menu item is simply omitted for the signed-in admin's own row in `/admin/users`) to prevent a self-lockout, since nothing in the spec addresses what happens if the only admin deletes themselves.
- **Reset-password reveals the new temporary password once, client-side only:** DESIGN.md's "Reset password?" confirm dialog doesn't show a next step, but the new temp password has to reach the admin somehow (same need as the "New user" form, which shows/edits it inline). Added a one-time reveal dialog with a Copy button after a successful reset, matching the "Share it with the user securely" messaging already used on user creation. The plaintext password is only ever present in that one API response — never stored or logged.
- **`generateTempPassword` split into its own dependency-free module:** `src/lib/password.ts` imports `bcrypt` (Node-only), but the "New user" dialog needs to generate/preview a temp password client-side. Moved the generator to `src/lib/temp-password.ts` (no Node deps) and re-exported it from `password.ts` for the server-side reset-password route, so both the client dialog and the API route share one implementation without bundling `bcrypt` into client JS.
- **Admin pages re-fetch via `router.refresh()` after mutations** rather than maintaining client-side cache/optimistic state: each `/admin/*` page is a server component that queries Prisma directly; its client child (`TeamsClient`/`UsersClient`/`SprintsClient`) calls the `/api/admin/*` routes for mutations and then calls `router.refresh()` to re-render the server component with fresh data. Simpler than hand-rolling cache invalidation, at the cost of a full server round-trip per action — acceptable for an admin CRUD screen that isn't the primary Excel-like table (that's the Sprint/Backlog view in step 4, which DESIGN.md explicitly calls for optimistic updates on).
